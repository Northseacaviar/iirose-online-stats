# iirose 在线状态监测器 — 产品文档

> 版本 v0.1(草案) | 2026-09-16 | 待技术选型确认后进入开发

## 1. 项目概述

监测社交网站 [iirose](https://www.iirose.com) 中不同状态在线人数的变化,周期性采集 **online、chatting、active、away、entering** 五类数据并保存在本地,提供图表展示五类数据的走势变化。

- 采集频率:默认每 1 分钟一次,可配置
- 数据:本地持久化,长期积累
- 展示:五条数据曲线的走势图
- 运行环境:Windows 11(用户个人电脑)

## 2. 前期调研结论(重要)

### 2.1 核心发现:stats 是客户端本地计算的,没有服务端 API

通过对 iirose 网页客户端解码 JS(`messages_decoded.js`)的分析,终端 `stats` 指令的实现如下:

```js
case "stats":
    this.hasParam(t, "-m") && this.tools(2, "max"),
    o = this.tools(1, ...);
```

`tools(1)` 的实现是**遍历客户端内存中的全站用户列表**(`Assets.userJson`),按用户状态字段分组计数,**完全不请求服务器**。这意味着:

- 不存在可以直接查询 stats 的接口,任何人(包括我们)都必须先连入 iirose 并拿到用户列表,再本地计算;
- 统计数据是**全站全局**的(用户已确认:stats 输出为全站数据),与所在房间无关;stats 后可跟数字参数限制"房间人数排行"的显示条数,`stats -m` 是终端全屏开关;
- 计算逻辑是公开的(见 2.3),可以在任何采集方案中精确复刻;
- **联机实测修正(2026-09-17)**:游客(未注册)账号无法通过纯 WebSocket 连接创建——网页有机器人网关,游客需走网页"新的开始"流程;注册账号可直接登录 WS(已实测),故采集使用用户提供的账号,统计口径不变(仍为全站)。

### 2.2 iirose 底层通信协议

调研了开源项目 [iirosebot](https://github.com/XCWQW1/iirosebot)(Python 机器人框架)与 [electron-iirose](https://github.com/iirose-tools/electron-iirose)(官方客户端曾经的开源版):

| 项目 | 说明 |
|---|---|
| WebSocket 地址 | `wss://m.iirose.com:443`(网页客户端同款;旧裸端口 8777 已停用) |
| 登录 | 发送 `*` + JSON:`{"r": 房间ID, "n": 用户名, "p": md5(密码), "st":"n", "mo":"", "mb":"", "mu":"01", "fp":"@"+32 位随机字符}`(fp 为随机指纹,联机实测站点接受任意随机值,见 handshake.py) |
| 心跳 | 网页客户端每 2s 发送 `c` 保活(旧版 Electron 客户端曾每 6 分钟发 `u`) |
| 压缩 | 消息 > 256 字节时 gzip 并加 `0x01` 前缀字节;接收时首字节为 `0x01` 则 inflate |
| 用户列表 | 登录后服务器下发当前房间完整用户列表,之后以增量消息维护(加入/离开/状态变更)。iirosebot 已完整实现解析 |

### 2.3 stats 五项指标的精确计算逻辑

用户列表每条记录中,字段 `[11]` 是状态字符,含义:

| 状态字符 | 含义 | 归入指标 |
|---|---|---|
| `"5"` ~ `"9"` | 近 10 分钟内有动作 | **Chatting** |
| `"0"` ~ `"4"` | 较久无动作 | **Active** |
| `""`(空) | 挂机 | **Away** |
| `"*"` | 正在进入 | **Entering** |
| `"a"` | AI 机器人 | (A.I.,不计入上述四类) |

- **Online** = 用户列表总长度
- 终端还输出性别分布(None/Male/Female/Couple),不在本次需求内,但数据结构支持扩展

### 2.4 现状与风险

- **站点当前处于维护状态**:2026-09-16 访问 iirose.com 返回"网站维护中"页面,网页客户端路径均超时,无法现场联机验证协议(WebSocket 端口 8777 存活与否正在探测);
- 用户已有资产:iirose-auto-stats.user.js 油猴脚本,已实现"自动 Ctrl+S 打开终端并输入 stats",但未捕获输出、未保存、无图表;
- 客户端为混淆 JS,后续站点更新可能导致解码失效(但 stats 计算逻辑长期稳定的概率较高)。

## 3. 功能需求

### F1 数据采集
- 周期性地获取当前房间 online / chatting / active / away / entering 五个数值
- 默认间隔 60 秒,可通过配置文件修改(如 `interval_seconds`)
- 采集时记录时间戳(本地时间),写入本地存储

### F2 数据持久化
- 每次采集追加一条记录,程序重启后数据不丢失
- 存储格式见 §5

### F3 图表展示
- 一张折线图,5 条曲线分别对应 5 个指标
- 支持选择时间范围(最近 1 小时 / 24 小时 / 7 天 / 全部)
- 自动刷新(跟随采集节奏)
- 显示当前最新数值

### F4 运行方式
- 采集器作为后台进程长期运行,开机可手动启动(可选:自启动)
- 展示端与采集器解耦:关闭展示不影响采集

### 非功能需求
- 资源占用低:采集器在后台长期运行,不宜超过 50MB 内存
- 容错:网络断开/被踢下线/站点维护时自动重试,不崩溃,恢复后继续
- 隐私:账号凭据只存本机

## 4. 产品边界(暂不包含)

- 不做按房间细分的统计(可后续版本扩展:数据里本就含每人所在房间)
- 不做数据导出/报表(可在后续版本添加 CSV 导出)
- 不采集性别分布、AI 数量(数据结构预留)

## 5. 数据模型

```
采集记录 record:
  ts          datetime     采集时间戳(本地,精确到秒)
  online      int          全站在线总人数
  chatting    int          聊天中(近10分钟有动作)
  active      int          活跃(较久无动作)
  away        int          挂机
  entering    int          正在进入
```

## 6. 技术方案对比(备选)

### 方案 A:原生 WebSocket 协议客户端(推荐)

自研轻量客户端,直接连 `ws://m.iirose.com:8777`,登录后维护用户列表,按 §2.3 公式本地计算五项指标。参考 [iirosebot](https://github.com/XCWQW1/iirosebot) 的成熟协议实现。

| 优点 | 缺点 |
|---|---|
| 极轻量:无浏览器,内存占用 <30MB,可 7×24 后台运行 | 协议细节靠逆向,站点协议变更时需适配 |
| **无需账号**:游客身份即可拿全站用户列表 | 目前站点维护,联机验证要等恢复 |
| 不依赖网页 DOM/混淆 JS,无 UI 干扰 | |
| 数据是结构化的,无需解析终端文本 | |
| 采集与展示完全解耦,技术栈自由 | |

实现要点:复用 iirosebot 的握手、心跳、全站用户列表增量解析逻辑;自己实现 stats 分组计数(约 20 行)。

### 方案 B:Playwright 浏览器自动化

无头浏览器打开网页、登录(复用浏览器会话)、模拟 Ctrl+S → 输入 stats → 读取终端输出文本并解析。

| 优点 | 缺点 |
|---|---|
| 与人工操作路径完全一致,天然免疫协议变更 | 内存占用 ~300MB+,后台常驻偏重 |
| 利用站点自身客户端逻辑,无需复刻协议 | 依赖 DOM 结构,页面改版即失效(同样脆弱) |
| 不存密码(可复用登录会话) | 需解析终端彩色富文本,较繁琐 |

### 方案 C:油猴脚本 + 本地采集服务

在用户现有 iirose-auto-stats.user.js 基础上扩展:捕获 stats 输出,POST 到本机一个小型 HTTP 服务(负责存储与图表)。

| 优点 | 缺点 |
|---|---|
| 复用已有脚本,开发量最小 | 浏览器页面必须 24 小时开着 |
| 跟随用户正常浏览会话,无需额外登录 | 依赖 DOM,油猴脚本受页面改版影响 |
| 采集逻辑与网页版完全一致 | 与浏览器的生命周期耦合,不独立 |

### 展示端方案(与上述采集方案正交)

| 展示方式 | 说明 |
|---|---|
| 本地 Web 仪表盘(推荐) | 采集器内置小型 HTTP 服务,浏览器打开 localhost 即可看 ECharts 折线图;交互丰富、开发快 |
| 桌面窗口程序 | PyQt/Tkinter 原生窗口,无需开浏览器,但图表交互开发成本高 |
| 静态 HTML 文件 | 双击打开,JS 读本地数据文件;最简单,但浏览器本地文件限制较多 |

### 技术栈推荐

- 语言:**Python 3.11+**(方案 A 首选;iirosebot 即 Python,协议代码可直接参考;采集、存储、HTTP 一体)
- 存储:**SQLite**(单文件、免安装、够用)+ 可选 CSV 导出
- 图表:**ECharts**(本地 HTML 仪表盘,交互式缩放/时间范围切换开箱即用)

### 🔄 浏览器侧上报 —— 方案 C 变体已实现为备胎(2026-09-17)

调研确认 iirose 客户端自带「自定义 JS」功能(解码 `messages_decoded.js` 的 `externalCode`):

- 终端 `js` 命令弹窗可粘贴脚本 **URL**(存 localStorage `extJs`,空格分隔可多个)或**代码**(存 `extJsCode`);`js -s` 开关;每次页面加载结束(`Init.externalCode()`)自动以 `<script>` 注入页面执行(仅过滤含 `.imoe.xyz/` 的地址),纯代码则 eval 成 IIFE
- 脚本在页面上下文可直读 `Objs.mapHolder.Assets.userJson`(与 `stats` 同源),按同一公式算五桶 → POST 本机 `/api/ingest`(服务端已加 CORS + Private Network Access 放行头,同秒冲突时 WS 值优先)
- 定位:**备胎采集/交叉验证**——浏览器页面开着时顺手上报,WS 采集断线时不丢数据;局限是页面必须 24 小时保持打开(即原方案 C 的缺点),故不取代 WS 采集器
- 开启步骤见 browser-js/README.md(脚本本体:browser-js/collector.js,由本地端服务在 /js/collector.js 提供)
